# W88：5579 只全量三浪评估 + 后台扫描脱离 Web 生命周期

> 立项背景：2026-11-10 / 11-11 / 11-12 连续三次「后台扫描全部股票」在
> `收尾·三浪主升评估` 卡死，台账 `interrupted / 3506~3589 / 5579`、
> `job_id=null`、`n_results=0`。用户明确要求：**5579 只全部要三浪结论**，
> 不接受靠限流换稳定，需立项做收尾内存优化 + Web 按钮改独立进程。

## 一、三次失败的复盘（决定性证据）

| 任务 | 启动 | 终态 | 停点 |
|---|---|---|---|
| `5469be0e` | 11-10 22:08 | interrupted | 3506/5579 |
| `75ff7679` | 11-11 21:03 | interrupted | 3589/5579 |
| `e8c02987` | 11-12 21:00 | interrupted（11-12 22:57 补打） | **3506/5579** |

11-10 与 11-12 停在**完全相同的 3506 只**，说明不是偶发崩溃，是收尾推进到
约 2/3 时的确定性资源耗尽。

根因链条：

1. **配置**：`data/scan_wave3_override.json`（11-08 20:56）为
   `AUTO_TRIGGER=5600 / AUTO_MAX=5600`，代码默认 `500/200`。
   `5580 > 5600` 为假 → 自动限流不触发 → 全部 5579 只逐票评估。
2. **内存（本次定位的核心）**：`attach_wave3_to_results` 把 5579 只的
   **完整日/周/月 K（`items` + `returns_by_symbol`）全部堆在内存**，
   再一次性交给 `evaluate_portfolio`。每只约 1MB × 5579 → 数 GB。
   11-12 21:42 实测 Web 主进程 RSS 2.3GB（平时 558MB）、可用内存 189MB、
   swap 已吃 2.2G；22:46 服务器所有 TCP 入口全部 refused（ICMP 仍通），
   疑似 swap 抖动连带拖垮 frpc / sshd。
3. **架构**：Web 进程内 daemon 线程 + 进程池 worker 由 Web fork；
   按钮默认 `resume=False`，算完才一次性 `_write_scan_batch`，收尾在写库
   **之前** → 收尾卡住/进程一死，5579 只成果全废。
4. **可观测**：收尾阶段不更新进度心跳，`mark_stale(600s)` 只在打开状态页
   时补打，页面长时间看不到失败。

> 补充：`correlation_matrix` / `portfolio_risk` 的 O(C²) 只作用于
> `verdict=='候选'`，候选数远小于 5579，**不是本次爆内存的主因**；真正的
> 主因是 `items` 里全量完整 K 线。

## 二、W88-1：收尾内存优化（流式逐票评估）

### 设计

- `mystery/core/wave3.py::evaluate_portfolio` 新增可选参数
  `evaluated`（已逐票 `evaluate` 过的 assessment 列表）。传入时跳过
  「`items` → 逐票重算」，**组合层（筛候选 / 相关性 / 组合总风险 /
  `scale_down` 等比缩放仓位）仍是同一段代码**。
- `mystery/services/wave3_scan.py::attach_wave3_to_results` 收尾改为
  **逐票流式**：读一只 → `resample` → `wave3.evaluate` → 把完整 assessment
  追加进列表 → `finally` 显式断开日/周/月 K 引用（CPython 引用计数立即
  释放）。任意时刻内存里只有**一只票**的完整 K 线。
- 收益序列 `cand_returns` **只为候选保留**（相关性矩阵本来就只统计候选），
  非候选的数千个日期 dict 不再白白堆着。
- 循环结束调 `evaluate_portfolio(evaluated=assessments, ...)`，
  它会对**全部** assessment 原地重算 `scale_down`（含非候选 shares 置零），
  再统一生成 compact 写回结果行。

### 口径零变化的保证

| 项 | 保证方式 |
|---|---|
| 单票结论 | `wave3.evaluate` 参数与旧 `evaluate_portfolio` 内部的调用逐项一致（`equity/risk_pct/symbol/name/params=None/lot_size=100/max_position_pct=None/strict`） |
| 组合风险 / 缩放 | 仍调用**同一个** `evaluate_portfolio`，未复制逻辑 |
| 非候选票 `wave3` 字段 | `evaluated` 传全部 assessment（不是只传候选），组合层照常对非候选置零 / 写 `scale_down` |
| 异常降级 | `evaluate_portfolio` 被注入异常时仍走同一个 `try/except` 边界（W69 回归覆盖） |
| 评分 / 信号 / 缓存键 / `RULE_VER` | 未改动 |

新增测试 `test_stream_path_identical_to_legacy_items_path` 把新旧两条路径的
完整返回做 **JSON 逐字段对拍**，任何口径偏差都会直接失败。

### 效果

峰值内存从「5579 × ~1MB 完整 K 线（数 GB）」降到
「单票 ~1MB K 线 + 5579 × KB 级 assessment + 候选收益序列」，约百 MB 级。
`MAX=0` 强制全量 5579 只不再 OOM，**自动限流从此只是省时间的可选项**。

### 顺带修正

`AUTO_MAX >= 池大小` 时旧代码会误报 `auto_limited=True`（UI 显示
「仅评估前 5600 只」但实际全评）。条件改为
`0 < auto_max < len(results)`，此类情况标 `cap_reason="none"`。

## 三、W88-2：Web 按钮改独立进程

### 设计

```
Web 按钮
  └─ components._bg_launch(scan_kind=...)
       ├─ bg_task_log.log_start(...)          # 台账留痕（含 scan_type）
       └─ scan_launcher.launch(...)
            ├─ 优先 systemd-run --user --unit=czsc-mi-scan-<tid> --collect
            │    （独立 cgroup / 会话，Web 重启、被 kill 都带不走扫描）
            └─ 回退 Popen(start_new_session=True)
                 └─ czsc-mi scan --market|--watchlist --resume --bg-task-id <tid>
                      ├─ --resume：按 chunk 增量落库 + 断点续跑
                      └─ CLI 自己写 log_progress / log_finish 台账
```

关键改动：

| 文件 | 改动 |
|---|---|
| `mystery/services/scan_launcher.py` | 新增。构造 argv、拉起独立进程、日志落盘、`MYSTERY_DB_PATH` 注入；**不硬编码本机路径**（CLI 由 `sys.executable` 同目录推导，符合 AGENTS.md §0） |
| `mystery/apps/cli.py` | 新增 `--market`（取消全市场默认 100 只防呆）、`--bg-task-id`；`_cmd_scan` 包装层写台账进度（5s/50 只节流）与终态；`_cmd_scan_body` 透传 `progress_cb/job_holder/result_holder` |
| `mystery/apps/web/views/components.py` | `_bg_launch` 支持 `scan_kind` 独立进程路径，旧 `fn` 线程路径保留兼容；`_bg_running_fragment` **改读 `bg_task_log` 台账**（跨进程可见），无条件渲染 |
| `mystery/apps/web/views/scan.py` | 两个后台按钮改传 `scan_kind`，不再 lambda 调 `scan_market` |

### 为什么能解决三次失败

- Web 重启 / OOM / 刷新页面 → 扫描在独立 unit 里继续跑；
- `resume=True` 每个 chunk 完成即 `_append_scan_results`，即使三浪收尾
  二次失败，个股结果也已在库，不会 `n_results=0`；
- CLI 每 5 秒写台账心跳，`mark_stale(600s)` 不会误判，页面始终能看到
  进度（独立进程不写 Web 内存字典，所以必须读台账）；
- Web 进程 RSS 不再承担全量扫描 + 三浪收尾，内存压力与 Web 解耦。

## 四、线上配置（用户诉求：全部要三浪结论）

`data/scan_wave3_override.json` 当前仍是 11-08 写入的
`5600/5600`。W88 修正后，池 5580 只时 `5600 < 5580` 为假，不会限流，
**不改也能全量评估**。但为避免未来股票池增长到 >5600 触发限流，建议改为
语义明确的显式强制全量（备份后覆盖）：

```json
{
  "MYSTERY_SCAN_WAVE3": "1",
  "MYSTERY_SCAN_WAVE3_MAX": "0",
  "MYSTERY_SCAN_WAVE3_STRICT": "0"
}
```

`MAX=0` 是「显式设置」，自动限流分支整体让位，任何池大小都全量评估。
热生效，无需重启 Web，只对**下一次**扫描生效。

> 红线：`AUTO_TRIGGER` 不要调到 >= 股票池数量，否则自动限流永不触发；
> 想限流时 `AUTO_TRIGGER` 必须远小于池大小。
