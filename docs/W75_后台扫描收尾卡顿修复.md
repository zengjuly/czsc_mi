# W75 — 修复「后台扫描任务一直卡在最后」（超大池三浪收尾卡顿）

> 版本：v0.10.34 ｜ 用户报告：「后台扫描任务一直卡在最后」
> 仓库权威状态见 `DESIGN_DOCUMENT.md` §9（W20–W75）。

## 1. 现象与根因

Web「全市场扫描」页点「🚀 后台扫描全部股票」后，进度条走到
`5580/5580`（100%）就一直停在「运行中」，长时间不结束、不写库；服务还
中途重启过（`NRestarts=2`），进程内存一度到 **2.2GB**。

只读诊断证据链：

| 证据 | 结论 |
|------|------|
| `.tasks.json` 心跳 `scan: done=5580,total=5580, pid=3400983(Web进程), updated=12:40:29` | 逐票扫描已跑完，卡在其后 |
| `scanlock` 曾被 Web 进程持有（后随进程消失而释放） | 卡在持锁的收尾段 |
| `scan_jobs` 最新仍是 11-06，本次全市场未写库 | 卡在 `_write_scan_batch` 之前 |
| 进程 2.2GB RSS、服务中途重启 | 收尾把全市场日/周/月 K 全驻内存 |

根因在 **W69 三浪附加**（`attach_wave3_to_results`）：它在逐票扫描
`done=total` **之后**收尾执行，且：

- `MYSTERY_SCAN_WAVE3_MAX` 默认 `0`（不限）→ 对全部 5580 只逐只
  `_daily_from_db` 查库 + `resample_bars` 周/月 + 三浪评估；
- `wave3.evaluate_portfolio` 对候选算 **O(C²) 相关性矩阵**（纯 Python 双层
  循环，实测 600 候选 18 秒，外推上千候选十几分钟、全量约 25 分钟）；
- **收尾阶段完全不报进度**（`progress_cb` 只在逐票循环里），心跳停在
  100%，Web 后台任务字典 `status=running` 永远不翻 `done` → 页面无限转圈。

即「慢」与「不可见」叠加，用户看到的就是「一直卡在最后」。

## 2. 修复（service 层，core 零改动）

不改变综合评分、三类信号、`RULE_VER`、三浪字段结构；不改 core 纯函数（保护
W68 39 项金标与 W69 回归测试）。

### 2.1 超大池自动限流（治本）

`mystery/services/wave3_scan.py::attach_wave3_to_results`：

- 仅当 **`MYSTERY_SCAN_WAVE3_MAX` 未显式设置** 且 `len(results) >
  MYSTERY_SCAN_WAVE3_AUTO_TRIGGER`（默认 **500**）时，自动只评估按分降序前
  `MYSTERY_SCAN_WAVE3_AUTO_MAX`（默认 **200**）只，其余标「未评估」；
- 小池（自选股 168 只、常规 CLI/日报）**行为完全不变**；
- **显式设置 MAX 完全尊重用户语义**：`MAX=5` 只评 5 只；`MAX=0` 强制
  全量、一键回退到 W69 旧行为；
- 组合摘要新增 `auto_limited / cap_reason / cap / pool_size`，
  `wave3_summary_line`（日报/Web/CLI 共用）追加
  「超大池自动限流(评估前 N/总数 只)」，限流完全可观测。

> 组合总风险本就只对「候选」有意义，对 5580 只全量算相关性矩阵既无意义
> 又是性能灾难；W69 原注释「防止超大股票池拖慢扫描」正是此开关的设计意图，
> W75 只是把默认从「不限」改为「大池自适应」。

### 2.2 收尾阶段进度可见（治标）

- `attach_wave3_to_results` 新增可选 `progress_cb`，逐票收尾上报
  `(k, n_picked, "收尾·三浪主升评估")`；
- `scan.py` 的 `_attach_wave3 / _persist_or_return / _scan_market_impl` 透传
  `progress_cb`，写库前再报「收尾·写入扫描结果」；
- `_cb` 收尾阶段**心跳保持满进度 + 阶段 label**（不回退到 `0/200` 造成误导），
  逐票阶段行为不变；Web 后台任务显示收尾独立刻度；
- `components.py::_bg_launch` 的 cb 支持第 3 参数 `stage`，记录 `updated`
  时间戳。

### 2.3 僵尸任务防护

`components.py::_bg_running_fragment`：

- 区分「逐票扫描 / 收尾阶段 / 疑似失联」三态；
- running 且超过 `_BG_STALE_SECONDS`（默认 **600 秒**）无任何进度/阶段更新
  → 显示「疑似失联/卡住」提示 + **清除该卡住的任务** 按钮，不再无限转圈
  （覆盖线程崩溃、进程被 OOM 杀但 `@st.cache_resource` 字典残留等场景）。

## 3. 实测（生产库，只读）

| 场景 | 收尾耗时 | 说明 |
|------|---------|------|
| 修复前 全市场 5580 只 | ~25 分钟 + 2.2GB 内存（推算） | 页面停在 100% |
| 修复后 600 只 results（未设 MAX） | **4.45s** | `auto_limited=True`，评 200 只、400 只未评估 |
| 修复后 显式 `MAX=0` 全量 200 只 | 4.22s | `auto_limited=False`，与 W69 旧行为一致 |

## 4. 配置与回退

| env | 默认 | 说明 |
|-----|------|------|
| `MYSTERY_SCAN_WAVE3_MAX` | 未设置 | 显式设置则完全尊重；`0`=强制全量回退 |
| `MYSTERY_SCAN_WAVE3_AUTO_TRIGGER` | 500 | results 超过此数才自动限流 |
| `MYSTERY_SCAN_WAVE3_AUTO_MAX` | 200 | 自动限流时评估的前 N 只 |
| `MYSTERY_SCAN_WAVE3` | 1 | 置 0 整个跳过三浪附加（W69 原开关） |

## 6. 影响面

- 仅影响「三浪附加」这一附加策略的收尾性能与可观测性；主扫描结果、评分、
  信号、写库行数、`RULE_VER` 均不变。
- 超大池扫描的 `wave3` 字段：前 200 只正常评估，其余「未评估」（Web/日报
  已有字段缺失显示 `-` 的兼容逻辑）。
- 自选股/小池扫描零变化。
