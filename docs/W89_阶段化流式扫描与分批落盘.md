# W89：阶段化流式全市场扫描与分批落盘（v0.10.47）

## 1. 问题：为什么过去「不能」分批落盘

用户质疑：*为什么不按大盘 → 板块 → 个股的顺序、每个标的一次做完完整分析、
每 10 个一批落盘？无论如何都不应该 OOM。*

这个质疑成立。11-10 / 11-11 / 11-12 三次全量扫描卡死在「收尾·三浪主升评估」，
表面原因是 `attach_wave3_to_results` 把 5579 只完整日/周/月 K 堆进内存，
**但更深层的原因是架构把「逐票落盘」和「全池合成」绑死了**：

| 全局耦合字段 | 产生位置 | 为什么绑死落盘 |
|---|---|---|
| `wave3_portfolio`（组合总风险、缩放、高相关对数） | `evaluate_portfolio`，需全池**候选** | 旧代码把它挂到**每一条** `payload_json` |
| `scale_down` / `shares`（等比缩放后仓位） | 同上，`for a in evaluated` 原地重算 | 非候选也要被置零，必须全部算完才知结果 |

于是「写第 10 条记录」必须等「全池 5579 只的组合风险算完」，
`results` 列表、`assessments`、`row_by_sym`、`assigns` 全都驻留内存，
落库被推迟到收尾之后。W88 消除了 GB 级 K 线，但没有拆开这个耦合。

其余遗留问题（W88 后仍存在）：

- `scan.py` 的 `results` 全量 list（`extend` / `append`）；
- `_resume_results` 把整个 job 读回内存做三浪，再全量 `UPDATE` 回写；
- 线程池回退分支一次性落库；
- 各大指数在个股**之后**才并入，且没有独立板块阶段。

## 2. 解法：四阶段流水线 + 全局层 SQL 回填

新增 `mystery/services/streaming_scan.py`，严格按用户要求的顺序：

```
① 大盘（8 个宽基指数，完整研判）
   ↓
② 板块（关注板块，价格/形态/强度/吸筹/相关个股）
   ↓
③ 个股（逐票完整分析，每 10 只一批落盘）
   ↓
④ 组合层（KB 级 assessment 合成 → SQL json_set 回填）
```

### 阶段 ③ 是核心

每只票在批次内完成**全部个股级分析**：综合评分、三类信号、K 线组合形态、
主力吸筹、三浪 `wave3.evaluate` 与单票仓位建议。然后：

- 每 `batch`（默认 **10**）只一批 `INSERT OR REPLACE` + `COMMIT`，
  主键 `(job_id, symbol)` 幂等；崩溃最多丢当前批，`--resume` 可续跑；
- 同步写出 JSONL 分片文件，每批 `flush()` + `os.fsync()` 后才算落盘；
- 批对象 `clear()` 显式断开引用，CPython 引用计数立即释放完整结果 dict；
- 单票 K 线在 `_wave3_one` 的 `finally` 中逐票置空，峰值只有**一只票**的 K 线。

### 阶段 ④ 解开全局耦合

内存里只保留两类 KB 级跨票状态（组合层数学上必需的最小集）：

- `assessments`：每票精简 assessment，**不含 K 线**（5579 只约 1~2 MB）；
- `cand_returns`：**仅候选**的收益序列，用于相关性矩阵。

调用与旧路径**同一个** `wave3.evaluate_portfolio(evaluated=...)` 得到
`scale_down` 与组合摘要，再用 SQLite `json_set` **在 SQL 层**回填：

```sql
-- 逐票最终 compact（含缩放后仓位），参数只有 KB 级 JSON
UPDATE scan_results
SET payload_json = json_set(payload_json, '$.wave3', json(?))
WHERE job_id=? AND symbol=?;

-- 组合摘要挂到每条个股行（指数行无 wave3，自动排除）
UPDATE scan_results
SET payload_json = json_set(payload_json, '$.wave3_portfolio', json(?))
WHERE job_id=? AND json_type(payload_json,'$.wave3') IS NOT NULL;
```

**全程不把已落盘的 `payload_json` 读回 Python 内存**。这是与
`_resume_results`（读回全量 rows 再全量 UPDATE）的本质区别。

### 内存上界

```
峰值 = O(batch × 单票完整 dict + 单票 K 线) + O(池大小 × KB 级 assessment)
     ≈ 几十 MB（与 5579 只完整 K 线的数 GB 彻底解耦）
```

落盘完成后 CLI 才读回**轻量**结果（无 K 线、`wave3` 为 300B compact）
供打印 / 日报 / Web，属展示契约，不是扫描执行期数据；Web 页面本身直接读
库表与台账，从不物化全量。

## 3. 阶段顺序与「每个标的分析完整」

| 阶段 | 产出 | 落盘位置 |
|---|---|---|
| ① 大盘 | 8 个指数：年线位置、MA 排列、涨跌幅、日/周 K 组合形态、吸筹 | `scan_results`（`is_index=True`，沿用 W84 口径）+ `01_index_*.jsonl` |
| ② 板块 | 板块自身：价格视图、强度分、日/周 K 形态、吸筹、强相关个股 | `02_sector_*.jsonl`（**不进** `scan_results`） |
| ③ 个股 | 评分 / 信号 / K 线形态 / 吸筹 / 三浪个股级结论 / 单票仓位 | `scan_results` + 每 10 只 `03_stock_*.jsonl` |
| ④ 组合层 | `scale_down`、`wave3_portfolio` 组合摘要 | SQL `json_set` 回填 + `04_portfolio_*.jsonl` |

**板块阶段为什么先于个股、且不进结果表**：
`analyze_focus_sectors(results=...)` 的 `auto` 关注板块解析与「强相关个股附
本期结论」原本依赖个股结果。按用户要求把板块提前后，阶段 ② 只做板块**自身**
完整研判（`results=None`，相关个股仍给出真实 Pearson 相关系数，只是不带当期
评分/建议）；个股的当期结论由阶段 ③ 产出，可按 symbol 关联。板块结果写分片
文件而非 `scan_results`，避免污染既有 Web 结果表与日报渲染（它们按
`is_index` 区分指数、其余均视为个股）。日报的板块区块本就由
`analyze_focus_sectors` 独立生成，不依赖本表。

**中断安全性**：阶段 ④ 之前任何时刻进程被杀，已落盘的每只票都带有**完整的
个股级三浪结论**（含单票仓位建议），不是半截记录；旧路径在收尾崩溃则是
`job_id=null / n_results=0`，成果全废。

## 4. 分流条件（零回归）

`scan_market` 在 codes 确定、行情同步之后分流。仅当**全部**满足才走 W89：

- `scan_type in ("market", "full")`；
- 非 `watchlist` / `universe` / `board` 自定义池；
- `no_persist=False`（调试路径不落库，保持原样）；
- 池大小 ≥ `MYSTERY_SCAN_STREAM_MIN`（默认 200，小池走旧路径）；
- 三浪为**全量口径**：显式 `MYSTERY_SCAN_WAVE3_MAX=0`，或未触发自动限流。

其余情况（自选、板块、前台 limit 小池、显式三浪上限、默认自动限流）
全部保持旧路径，既有测试与结论口径零回归。

> 为什么「按分降序取前 N」的限流不能流式：必须等全池分数齐了才知道
> 「前 200」是谁，与逐票落盘语义冲突，因此回退旧路径。
> 线上 W88 已设 `MAX=0`（显式全量），不受影响。

`MYSTERY_SCAN_STREAMING=0` 可一键整体回退。

## 5. 配置项

| 环境变量 | 默认 | 说明 |
|---|---|---|
| `MYSTERY_SCAN_STREAMING` | `1` | `0` 关闭流式，回退旧路径 |
| `MYSTERY_SCAN_STREAM_BATCH` | `10` | 每批落盘只数 |
| `MYSTERY_SCAN_STREAM_MIN` | `200` | 启用流式的池大小下限 |
| `MYSTERY_SCAN_STREAM_SHARD` | `1` | `0` 关闭 JSONL 分片（DB 仍分批落库） |
| `MYSTERY_SCAN_SHARD_DIR` | `<db>/scan_shards` | 分片目录，按 job 分子目录，保留最近 3 份 |
| `MYSTERY_SCAN_WORKERS` | `4` | 并行度（进程池 chunk=16，落盘仍按 batch=10） |

## 6. 口径一致性

- 评估参数（`equity` / `risk_pct` / `strict` / `MIN_BARS`）、取数
  (`_daily_from_db`)、周月线派生 (`resample_bars`)、压缩 (`_wave3_compact`)、
  组合摘要 (`_wave3_portfolio_summary`) **全部复用 W88 同一批函数**，未另写一套；
- 组合层仍走同一个 `evaluate_portfolio`，非候选票同样被原地置零，
  逐字段口径不变；
- `assessment.symbol` 是归一码、`scan_results` 主键是原始码，
  阶段 ④ 显式维护 `raw_by_norm` 映射，避免回填行匹配不上；
- 返回前按「分数降序 + 指数末尾」排序，与旧路径
  `results.sort()` 后再 append 指数的顺序一致。

## 7. 测试与验证

`tests/test_w89_streaming_scan.py`（18 项，全绿）覆盖：

- 分流条件（含自动限流回退、env 一键关闭）；
- **每批 ≤ 10 只落盘**、分片文件每文件 ≤ 10 行、批对象落盘后清空；
- 流水线不持有全量完整结果、assessment 不含 K 线；
- 严格阶段顺序 `index → sector → stocks → portfolio`；
- 最终落库 `wave3` / `wave3_portfolio` 与旧 `attach_wave3_to_results`
  **逐字段对拍**；
- 阶段 ④ 之前中断，每只票仍有个股级完整三浪结论；
- 断点续跑按已落盘 symbol 幂等跳过；模拟中途崩溃仍保留已完成批次。

全量回归 **716 passed / 6 skipped**，integration **9 passed / 6 skipped**，
零失败、未改动任何既有测试断言。

## 8. 已知边界

- 组合层必须保留 O(池大小 × KB) 的 assessment（相关性矩阵与总风险预算是
  跨票量），这部分无法降为 O(batch)，但已是与 GB 级 K 线解耦的最小集；
- 阶段 ② 的强相关个股不带当期评分/建议（个股尚未分析），只有真实相关系数；
  如需附带，可在个股阶段完成后按 symbol 关联回填；
- 分片文件保留最近 3 次 job，每次约 5579 行 JSONL，磁盘占用可控。
